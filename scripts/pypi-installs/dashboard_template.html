Who installs scikit-learn and related packages

Read this first. This is one possible way to read the public download logs, to try to get some insights. Downloads are not users: one CI job or one Docker build is a download each time it runs, and a user with a warm cache is none. The splits below rely on what the installers report and on heuristics. These numbers might not be representative of anything. Read the methods and limits before quoting one.

Summary

Click a column to sort.

  • All downloads is the number usually quoted. It includes mirrors and scrapers.
  • By an installer: by . All the numbers below are about these downloads.
  • In CI: the installer saw a CI environment variable. Only pip and uv report it, so this is a lower bound.
  • Desktop: downloads from Windows and macOS outside of CI. This is the closest thing to people installing the package on their own machine, and I think the most comparable number between packages. It misses the people on Linux, so it is unfair to Linux-only packages like cuml.

Who downloads

  • Linux, not CI mixes servers, containers, cloud notebooks, CI that is not flagged and Linux desktops. It can't be split further.
  • Weekend / weekday: downloads of an average Saturday or Sunday over those of an average weekday. Scheduled jobs give 1, people at work give a low value.
  • Fingerprints: number of distinct (country, installer, OS, Python version, glibc version, CI flag). Top fingerprint is the share of the downloads that come from the largest one. A high value on a small package means that one machine or one pipeline makes the number (see the details).

Methods and limits

  • Sources. The PyPI download logs, queried from the public ClickHouse instance behind clickpy.clickhouse.com. The release dates come from the PyPI JSON API. The conda numbers come from the monthly files of anaconda-package-data.
  • A download is not an install, and not a user. pip and uv cache the wheels: reinstalling in a new environment on the same machine is often not a download. A CI job or a Docker build without cache is one each time. So the numbers measure how often the package is fetched, mostly by machines.
  • By an installer. The user agent says which tool downloads. Mirrors (bandersnatch, Nexus, Artifactory), browsers and scripts are dropped. People behind a company mirror are invisible: the mirror downloads each file once.
  • CI. pip and uv report since whether a CI environment variable is set. poetry, pdm and old pips don't, and a Docker build started by CI does not see the variable. So the CI share is a lower bound, and Linux, not CI still has a lot of automation.
  • Desktop. Windows and macOS outside of CI. Servers and containers almost never run these OSes, so these downloads are mostly from laptops and workstations. It still counts each new environment of the same person, misses WSL and Linux desktops, and misses conda users.
  • Fingerprints. The logs have no IP address or user id. Distinct fingerprints saturate on a popular package (a few thousand combinations exist), so this only tells how spread the downloads are, not how many users there are.
  • Countries are those of the IP address: the US share is mostly cloud regions.
  • conda. Monthly counts per channel, published a few days after the end of the month, with CI and mirrors included. The nightly channels are left out.
  • Period. days is short: a release, a holiday or one misconfigured pipeline moves the numbers. Check the monthly plots before reading a change as a trend.
